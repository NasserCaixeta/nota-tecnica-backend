# Stripe no piloto — configuração e validação

O usuário substituiu o Asaas pelo Stripe em30/10/2026. Nada do Asaas é necessário para o funcionamento atual: conta, API, webhook e Sandbox anteriores não são usados. O marcador interno `environment=sandbox` significa apenas ambiente de testes do Stripe. Migrações/relatórios históricos preservam o nome do provedor anterior para não reescrever auditoria.

## Credenciais privadas

Arquivo local `.env.sandbox` (fora do Git, modo0600):

```dotenv
STRIPE_SECRET_KEY=
STRIPE_WEBHOOK_SECRET=
PAYMENTS_ENABLED=false
PAYMENTS_ENVIRONMENT=sandbox
PAYMENTS_HISTORY_PRICE_CENTS=1900
PAYMENTS_SUBSCRIPTION_PRICE_CENTS=4900
PAYMENTS_CALLBACK_BASE_URL=http://localhost:5173
FRONTEND_URL=http://localhost:5173
BACKEND_CORS_ORIGINS=["http://localhost:5173"]
```

Preencher `STRIPE_SECRET_KEY` com chave secreta de testes (`sk_test_`, `rk_test_` ou `rkcs_test_`); chave pública ou live é rejeitada. Preços acima são valores explícitos de simulação, não definição comercial. O segredo `whsec_...` vem do Stripe/CLI, não é uma senha arbitrária. Não colocar nenhuma chave em VITE, chat, print, commit ou comando que exponha valor na lista de processos.

A chave foi solicitada ao usuário para o arquivo privado; sua existência é verificada apenas por booleanos/prefixo, sem imprimir seu valor. Credenciais Asaas locais antigas não são reutilizadas.

## Desenvolvimento local

A aplicação e o worker devem carregar `.env.sandbox`; o banco dedicado local é `nota_tecnica_sandbox`, separado das fixtures destrutivas `_test`. Redis DB14 é reservado ao runtime local; integração usa DB15. Aplicar migração0018 antes de iniciar serviços.

```sh
uv run --env-file .env.sandbox alembic upgrade head
uv run --env-file .env.sandbox uvicorn app.main:app --host 127.0.0.1 --port 8000 --no-access-log
uv run --env-file .env.sandbox celery -A app.integrations.queue.celery_app:celery_app worker --loglevel=WARNING
uv run --env-file .env.sandbox celery -A app.integrations.queue.celery_app:celery_app beat --loglevel=WARNING --schedule=/tmp/nota-tecnica-stripe-beat
```

A [Stripe CLI](https://docs.stripe.com/cli) encaminha eventos assinados sem túnel público. Configurar autenticação de teste de forma privada (`stripe login --interactive`, ou `STRIPE_API_KEY` no ambiente do processo); se usar `STRIPE_SECRET_KEY` no arquivo da aplicação, injetar seu valor como `STRIPE_API_KEY` somente no ambiente da CLI. Não imprimir a chave.

```sh
stripe listen --forward-to http://127.0.0.1:8000/api/v1/payments/webhooks/stripe
```

Copiar o signing secret informado pela CLI para `STRIPE_WEBHOOK_SECRET` e reiniciar API/worker com a configuração. `PAYMENTS_ENABLED=true` só depois de chave, segredo e preços prontos. HTTP de callback só é aceito para loopback em local/test; piloto público permanece HTTPS. Em ambiente público, criar endpoint Stripe com URL HTTPS e versão2026-10-28.endive; usar o segredo desse endpoint, diferente do segredo local da CLI.

A CLI também oferece Sandbox temporário sem cadastro, com expiração de7dias; como o usuário já possui chave, não criar uma segunda conta automaticamente.

## Contratos e segurança

- Checkout hospedado em `checkout.stripe.com/c/pay/cs_test_*`, cartão de testes, produtos avulso/recorrente e preços calculados pelo servidor.
- API fixada em `https://api.stripe.com/v1`, versão2026-10-28.endive; todos os recursos canônicos exigem livemode=false. Não há fallback Asaas nem aceite de produção.
- Metadata server-side liga pedido e comprador; Customer.metadata.user_id + e-mail identifica o proprietário. CPF fica local e não é enviado ao Stripe.
- Raw body do webhook até128KiB; HMAC Stripe-Signature, tolerância±300s, inbox transacional e recuperação de fila. Retorno/checkout completo isolado não concede benefício.
- Pagamento avulso confirma PaymentIntent; assinatura confirma invoice com pagamento de cartão, linha mensal e período daquela invoice. Refund/disputa por Charge/PI converge para o mesmo recibo da invoice. Lock PostgreSQL usa ID canônico para impedir duplicação entre aliases.
- Timestamps Stripe têm precisão de segundos: comparar criação local nessa mesma precisão, mantendo 720horas exatas do timestamp confirmado. Datas sem hora e instante futuro continuam recusados.
- Criação usa Idempotency-Key estável. Reconciliação sem ID conhecido só pode repetir esse mesmo pedido nas primeiras23horas; depois, reconciliação administrativa, sem gerar outra compra silenciosamente.
- Cancelamento define cancel_at_period_end=true e preserva período já pago. Estorno/contestação financeira canônica revoga o benefício respectivo.
- Pedidos antigos são identificados como provider=asaas pela migração0018; eventos/cancelamentos antigos não são enviados ao Stripe. Direitos legítimos históricos continuam sujeitos à validade já registrada.

## Verificação local e remota

Comandos backend (PG/Redis locais descartáveis):

```sh
uv run ruff check app tests alembic
uv run ruff format --check app tests alembic
TEST_POSTGRES_URL=postgresql+asyncpg://nota_tecnica:nota_tecnica@localhost:55439/nota_tecnica_pilot_test TEST_REDIS_URL=redis://localhost:55440/15 uv run pytest -q
```

Frontend: `npm run lint`, `npm run test -- --run`, `npm run build`, `npm audit --audit-level=moderate` e `PLAYWRIGHT_BROWSERS_PATH=/private/tmp/nota-tecnica-playwright npm run test:e2e`. As seis jornadas usam servidores HTTP reais, PostgreSQL migrado e eventos Stripe assinados, com gateway/storage controlados só no processo de testes. Isso não é homologação remota.

Homologação remota pendente até chave/segredo disponíveis: criar Checkout avulso e mensal reais no ambiente de testes, usar cartão oficial de testes, confirmar evento autenticado e benefício; reenviar evento e confirmar idempotência; cancelar renovação, testar estorno e fim do período. Não usar cartão real. Registrar somente IDs sanitizados/resultados, nunca chave, dados de cartão ou URL privada de checkout.

Resultados, SHAs e revisão serão acrescentados após os commits/verificações finais desta entrega.
